# Tool-calling LoRA trainer — send to your GPU computing center

Turnkey. **No editing, no Hugging Face account/token, no pre-installed models.**
Send this folder to the center, build the container once on a login node, submit
one job — get back a LoRA adapter for Llama 3.2 1B plus a GGUF copy ready for
`llama-server`. The build downloads the (ungated) base model and llama.cpp and
**bakes them into the image**, so the GPU compute node runs fully offline.

## Pick the path that matches the center

### A. Slurm + Apptainer/Singularity — typical HPC, no Docker needed
On a **login node** (has internet), build the `.sif` straight from the definition
file, then submit:
```bash
apptainer build toolcall-lora.sif apptainer.def   # or: singularity build ...
sbatch run.slurm
```
The compute node needs no internet and no token — model, data, and tooling are
baked into the `.sif`. Output lands in `./out/toolcall-lora/` (bind-mounted).

### B. Docker + GPU (a cloud VM or any node where you have Docker)
```bash
bash run_local.sh
```
Builds a self-contained image (model baked in) and runs it → `./out/toolcall-lora/`.

### C. Bare GPU node, no container runtime
```bash
bash run.sh
```
Bootstraps a venv, installs torch + deps, downloads the model + llama.cpp into
`./assets`, trains → `./out/toolcall-lora/`. (Internet needed once, for the
downloads.)

## What you get back

`out/toolcall-lora/`:
- `adapter_model.safetensors` + `adapter_config.json` — **the adapter** (tens of MB)
- `toolcall-lora.gguf` — same adapter for `llama-server --lora`
- `training_meta.json` — provenance

## Files

| file | role |
|---|---|
| `apptainer.def` | **HPC-native container build** (no Docker needed), model+data baked in |
| `run.slurm` | Slurm job — runs the Apptainer/Singularity `.sif` on a GPU node |
| `Dockerfile` / `run_local.sh` | Docker image + runner (cloud VM / Docker node) |
| `run.sh` / `setup.sh` | bare GPU node (no container): venv bootstrap + run |
| `train_lora.py` | the trainer — transformers + peft only, assistant-only loss |
| `download_assets.py` | fetch ungated base model + llama.cpp into `./assets` (no token) |
| `make_data.py` | **self-contained data generator** (stdlib only, no parent project) |
| `system_prompt.txt` | frozen serving prompt the data trains against |
| `requirements.txt` | pinned deps (torch: from the image, or `setup.sh` for bare nodes) |
| `data/toolcall.jsonl` | training rows — shipped, or regenerated by `make_data.py` |

## The base model (why no token is needed, and a correctness note)

Default base is `unsloth/Llama-3.2-1B-Instruct` — an **ungated mirror with the
same weights** as `meta-llama/Llama-3.2-1B-Instruct`, which is what Ollama's
`llama3.2:1b` serves. Same weights ⇒ the adapter is valid against the GGUF you
serve at home, and you never touch a login/token flow. To use the official gated
repo instead, set `BASE_MODEL=meta-llama/Llama-3.2-1B-Instruct` and export
`HF_TOKEN` — but you don't need to.

## Resources / time

A 1B LoRA on ~1,200 rows: **minutes to ~1 hour on one modern GPU**, ~8–16 GB
VRAM in bf16. Smaller GPU? add `--load-4bit` (QLoRA). One GPU is plenty.

## Knobs (optional — defaults are sensible)

```
--rank 16 --alpha 32      LoRA capacity (raise if underfitting)
--epochs 3 --lr 2e-4      schedule for a small set
--batch 8 --grad-accum 2  effective batch 16; lower --batch on OOM
--max-len 2560            harness system prompt is long; keep >= ~2048
--load-4bit               QLoRA for <16 GB GPUs
--base <id-or-path>       override the base model
TORCH_INDEX=...           setup.sh: different CUDA wheel (e.g. .../whl/cu118)
```

## After the adapter comes back

Serve it locally with the llama-server that ships with Ollama:
```
llama-server -m <llama3.2-1b.gguf> --lora out/toolcall-lora/toolcall-lora.gguf -c 4096
```
Toggle per request via `/lora-adapters`, point the harness at llama-server, and
rerun the 12 held-out benchmark tasks: `1B` vs `1B+adapter`. That delta is the
experiment.

## Where the data comes from (and how to make it if the folder is empty)

The training data is `(context -> correct tool-call JSON)` pairs in chat format.
It gets there one of two ways — both self-contained, no editing:

- **Shipped:** `data/toolcall.jsonl` is included (1,200 rows).
- **Generated in-place:** if `data/toolcall.jsonl` is missing, `run.sh` and the
  Docker build automatically run `make_data.py` to recreate it. To do it by hand:
  ```bash
  python make_data.py --n 2000 --out data/toolcall.jsonl
  ```

`make_data.py` is fully standalone (Python stdlib only — no torch, no parent
project). It slot-fills natural tasks and emits the ground-truth call, so every
row is correct by construction. Each row embeds `system_prompt.txt` — the frozen
serving prompt the adapter must train against — plus a share of multi-turn
"recover after an ERROR" rows that teach in-weights repair.

**If you change the harness tools or prompt**, re-snapshot the frozen prompt so
training matches serving, then regenerate:
```bash
# from the parent project (has the live harness):
python -c "from harness.agent import HARNESS_SYSTEM, SHAPE; from harness.tools import tool_docs; \
from harness.world import SIM_TODAY_HUMAN; \
open('training_scripts/system_prompt.txt','w',encoding='utf-8').write( \
HARNESS_SYSTEM.format(today=SIM_TODAY_HUMAN, shape=SHAPE, docs=tool_docs(True), memory_block='', extra_rules=''))"
python training_scripts/make_data.py
```

The richer data recipe — harvesting correct calls from `../results/` transcripts
and distilling from the 32B — lives with the project's
`../finetune/gen_toolcall_data.py`; mix those in and replace the file when you
want more coverage than the synthetic backbone.
